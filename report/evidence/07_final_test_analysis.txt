## 4. Explainability

Applied to the **best tree model on CV** (RF, XGB or DT, absolute or relative), because SHAP `TreeExplainer` is exact and fast for trees. For a relative version, built-in importance and SHAP describe the **deviation from yesterday** (`y − lag_24`), which is what the trees learn; permutation importance is measured on the final prediction (`lag_24` + deviation).

- *Built-in importance:* impurity reduction from splits on each feature; fast but biased towards features with many values.
- *Permutation importance:* shuffle one column of the test set and measure the RMSE increase (`n_repeats` shuffles); more reliable.
- *SHAP:* splits each prediction into additive feature contributions (kW).

--- CELL 28 (code; execution=12) ---
trees = [k for m in ['RF', 'XGB', 'DT'] for k in (m, m + DELTA_SUFFIX) if f'{k}-tuned' in fitted and k in s3.index]
EXPLAIN = s3.loc[trees, 'RMSE_mean'].idxmin()
model_x = fitted[f'{EXPLAIN}-tuned']
tree_x = model_x.regressor_ if isinstance(model_x, DeltaTarget) else model_x     # the fitted tree ensemble itself
target_x = 'deviation from lag_24' if isinstance(model_x, DeltaTarget) else 'load'
print('Explained model:', f'{EXPLAIN}-tuned', '| trees explain the', target_x)

builtin = pd.Series(tree_x.feature_importances_, index=MF)
perm = permutation_importance(model_x, Xt[MF], yt, scoring='neg_root_mean_squared_error',
                              n_repeats=3 if SMOKE else 10, random_state=RANDOM_STATE, n_jobs=N_JOBS)
perm_s = pd.Series(perm.importances_mean, index=MF)       # RMSE increase (kW) when shuffled

## 6. T13 and F20 – Comparison with the literature (indicative)

The test results of this project (h24 and h1) next to the results **reported** in the literature review (its Table 7) and in the surveyed GitHub repositories (`docs/literature_results.csv`). These are the studies' own numbers; their set-ups were **not** re-run here.

A fair comparison needs the same target, resolution, horizon, split and test period. **No study matches all five**, so this is a rough positioning, not a ranking. The extra columns show how comparable each row is:

- `same_target`: same quantity as this project (city total)?
- `horizon_vs_ours`: forecast horizon compared with this project (shorter horizons are much easier; "no load lags" means a nowcast from weather and calendar);
- `chronological_split`: train before test, without shuffling?
- `comparability`: overall judgement (not comparable / weak / moderate).

MAPE and R² do not depend on the unit of the target, but they still depend on how hard the target is: a single zone is noisier than the city total, and short horizons or shuffled splits make any model look better. RMSE and MAE only compare for the same target.

## 7. Business interpretation and summary

For the day-ahead problem the model is wrong by **1,095 kW per hour on average, about 1.72% of the mean load** (63,751 kW), half the error of "tomorrow looks like today". If reserve capacity is sized on forecast error, it could be roughly halved. The main risk is **rare religious holidays** (Mawlid was about 6% off), where a manual adjustment or extra reserve is advisable.

**RQ3 (accuracy vs cost):** SVR is the most accurate model but the slowest to fit (about 3.5 s); XGB_delta and RF_delta are only 8–12% worse in MAPE and fit in under 0.2 s; LR fits instantly but is about 50% worse. With about 8,000 rows every model is fast enough for daily operation, so accuracy should come first.
